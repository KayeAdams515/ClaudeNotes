# 完善 course-lecture-notes 技能的改稿提示词

> 用途：把评审发现的七处问题交回给她改，不改结构、不重写。
> 要点：每条都附证据与验收方式；已做对的部分明确保护起来。

---

## 可复制正文

```
# 任务

这份技能已经被人逐条核对过。结构没问题，要改的是七处。这是一次改稿，不是重写。

改稿规则：

1. 只改下面点名的位置，改动全部落在已有小节之内。不新增章节，不写"修订说明""附录""以上内容"。
2. 已经做对的部分一律不要动。特别是：每节开头的口吻与"你会看到……这时应当……"的句式、
   十二条"约束 + 正样本/资料卡反例"对照、墨迹部件的检查流程、"承诺—落点"对应、
   交付报告里"未执行的项目标为未验证"的要求。
3. 改完按顺序输出：① 改动清单（哪一节、删了什么、加了什么、为什么）② 完整新文档。
4. 某处若必须连带调整别处，在清单里单独列出并说明原因，不要悄悄改。

# 一、检查脚本有 bug，先修这一条

在一份**没有任何手写笔迹**的真实演示文稿上运行脚本，输出是：

    候选部件：
    ppt/notesMasters/notesMaster1.xml
    ppt/slideMasters/slideMaster1.xml
    ppt/slideMasters/slideMaster2.xml
    ppt/theme/theme1.xml
    ppt/theme/theme2.xml
    ppt/theme/theme3.xml
    指向候选部件的内部关系：
    （120 余行，全部是 notesSlide 指向 notesMaster）

原因：`markers = re.compile(r"inkml|inkdata|contentPart|<[^>]*ink\b", re.I)` 里的
`<[^>]*ink\b` 会命中主题与母版里的 `<a:hlink>`、`</a:hlink`、`<a:folHlink`，
以及 `clrMap` 属性中的 `hlink="hlink"`——"hlink" 的结尾正好是 "ink"，`re.I` 让它更容易命中。

真阳性那条路是正确的：一个含 `ppt/ink/ink1.xml` 的包，能报出该部件，以及
`ppt/slides/slide1.xml rId2 -> ppt/ink/ink1.xml`。所以只需要收紧匹配，不要改整体流程。

要求：

- 修掉误报，同时保证"墨迹部件 + 指向它的关系"仍然能被报出来。
- **在技能正文里加一个可以自己跑的自检**，用两个最小构造包，并写清各自应当输出什么：
  · 包 A：只有 `ppt/theme/theme1.xml`，内容含 `<a:hlink/>`、`<a:folHlink/>`
    与 `clrMap hlink="hlink" folHlink="folHlink"`。期望输出：候选部件为空，关系为空。
  · 包 B：含 `ppt/ink/ink1.xml`、带 `p14:contentPart` 引用的 `ppt/slides/slide1.xml`、
    以及 `ppt/slides/_rels/slide1.xml.rels`（Id=rId2，Target=../ink/ink1.xml）。
    期望输出：报出 `ppt/ink/ink1.xml`，并报出 `ppt/slides/slide1.xml rId2 -> ppt/ink/ink1.xml`。
  自检的代码放进技能正文，让以后的执行者改完能立刻重跑。
- 保留"报告中的数量是部件数量，不是手写处数"这句，并补一句：
  **脚本输出为空只是"没有结构命中"的起点，不是"无墨迹"的结论；结论仍要逐页看原件。**

# 二、删掉一条不可靠的引文，以及它支持的那个结论

现文写着"导出丢墨迹是需要实测的风险，而非所有软件共有的定律。PowerPoint 官方导出选项允许包含墨迹"，
并挂了 `support.microsoft.com/en-us/powerpoint/training/save-powerpoint-presentations-as-pdf-files`。

这条链接指向的不是那篇文章——Microsoft 支持文章的真实地址形如 `/en-us/article/<标题>-<文章GUID>`，
而这条既没有 GUID，路径也不是文章路径，是拼出来的。更关键的是，能查到的相关线索方向相反：
既有用户在问"为什么手写在导出 PDF 后没有保存"，也有第三方库专门提供"在 PDF 导出中隐藏/显示墨迹"的开关。

危害不在引错，而在这句话把"导出会丢墨迹，所以要查原包"这个最贵的教训软化了：
执行者读到这里，很可能跳过包内检查。

要求：删掉这句断言和那条链接，换成更硬的表述——
**不同工具链的行为不同，所以一律先按"会丢"处理，用包内检查去证实或否定；
在检查之前，不要根据任何导出图或预览图对墨迹下结论。**
其余"某些转换链会把整份独立墨迹都丢掉"的措辞是准确的，保留。

# 三、补上"一篇写完之后放什么"

现在"真正落笔时"那一节把推进链讲得很细，但没有规定收束。目标库每篇都有固定收尾，
检查与导航都依赖它。缺了它，产出的篇目和库内其他篇不像同一门课，
"回到开场说明卡点如何消失"这个动作也没有落地处。

在"落笔"那一节末尾补一段，写清一篇的骨架（措辞你可以自己组织，这些位置不能缺）：

    篇首：任务导读 → 阅读说明（来源与课堂证据状态）→ 一张画"问题如何演进"的路线图
    正文：从"## 0. 开场：一个具体场景"开始，按材料的节号推进
    收束：这一讲的三句话（只留三条）→ 速查表（名称 / 公式或判据）→ 下一讲预告
    导航：上一讲 ｜ 下一讲 ｜ 返回课程索引

三条要写的是"这一讲带走了什么判断"，不是内容摘要。速查表只放可查的式子与判据，
不放叙述。下一讲预告要留一个悬念，多篇连起来能读成一条线。

# 四、callout 的默认映射方向反了

现文给"新库默认：定义映射到 info，定理映射到 abstract"。目标库实际相反：
定义、定理、必须记住的结论一律用 `important`；`abstract` 专门留给"这一讲的任务"；
`info` 用于阅读说明与授课进度；`note` 用于补充、前后联系、拓展；`example` 例题；
`warning` 易错与勘误；`question` 提问；`tip` 速查与预告。

要求：把默认值改成"**库内已有的语义标签优先；确实没有同义标签，才退回 info/abstract**"，
并把上面这套映射作为已知实例写进去。不要让它看起来是通用定律——同一份技能会在不同课程里用。

# 五、frontmatter 的默认键会撞到自己立的规矩

现文默认 `title/course/order/sources/class_evidence`。目标库实际是
`title/course/chapter/section/tags/aliases/source`，而"课堂证据状态"在库内是篇首一个说明块，
不是字段。

问题在于：这跟你自己那条"不借本次整理默默统一已有课程的体例"是冲突的——
执行者若照这套键去补旧篇，正好违反前一条。

要求：明确两层——**新增字段只用于新建的课程库；已有库缺信息时写进正文的说明块，不改键、不删键。**
旧库里出现过的可选键（如教师姓名、备注类字段）照旧保留。

# 六、"不逐处插入出处"容易被读成"页码也删掉"

目标库的约定是：删的是"课件"这个称呼，**页码可以留作定位**（如 `（p.127）`）。
现文写"页码和转写时间范围集中到来源字段"，容易被执行成删掉全部页码。

要求：补半句——出处与来源集中写在 frontmatter 与索引里；正文中的页码是定位手段，可以保留。

# 七、四处小缺口

1. **表格里给图片加宽度必须转义**：写成 `![[图.png\|60]]`。不转义会把表格列截断。
   现文只写了双链别名的转义，漏了图片这条（目标库实测踩过）。
2. **板书图的命名契约**：`<章>.<节>-板书-<描述>.png`，裸文件名嵌入，不套 callout，
   也不写"圈出了什么、箭头指向哪里、用了什么颜色"。现文有"不写画面描述"，
   但没有命名约定与存放位置（课程附件目录）。
3. **"同一材料的 PDF 版与 PPTX 版未必重复"**：PPTX 可能多出整套手写板书。
   在向用户提出"这份和已有笔记重复、无需整理"之前，必须先查 PPTX 包内有没有墨迹部件。
   现文没有这条，而它正是包内检查最容易漏用的一次机会。
4. **`pdftotext` / `pdftoppm` 在 macOS 上默认不存在**。现文给了"换工具"的兜底，
   但执行者手上若只有 Python，就给一个等价写法（PyMuPDF 的 `page.get_text()` 与
   `page.get_pixmap()`），并说明两者输出的差异（排版保留与否、DPI 设置）。

# 八、交之前自己跑一遍

1. 跑第一节那两个最小自检，把两份实际输出贴出来。包 A 必须为空。
2. 通读改后的全文，确认没有新增章节、没有"修订说明/附录/以上"这类段落。
3. 确认第七节那四处是补进已有小节，不是堆在文末。
4. 只报实际做过的事。自检没跑就说没跑，不要写"已验证"。
```

---

## 用法

1. 整段贴进去。她不需要看评审过程，证据都写在里面了。
2. 她若把改动堆在文末，回一句：「改稿规则第 1 条：落在已有小节内。」
3. 收到后你只验两处：**第一节那两段自检输出**（包 A 为空才算修好），以及**改动清单是否只有这七处**。
