# C9.1 哈希表 Hashing

> [!abstract] 这一讲的任务
> 前面几章把"查找"做到了 $O(\ln n)$：二叉搜索树靠比较沿着一条路径往下走，AVL 与红黑树再把树高压到 $O(\ln n)$，于是 `get` 和 `put` 都是 $O(\ln n)$。这一讲要问的是那句 "Can we do better?"——想更快，就不能再**比较**，而要**直接算出位置**。
> 答案是哈希表 Hash Table：一个函数把键折算成一个数组下标，查找退化成一次下标访问，期望 $O(1)$。代价是彻底丢掉顺序，而且"冲突"永远无法消除——所以这一讲的正文，其实全是围绕两件事展开：**函数怎么设计**，**撞车之后怎么办**。

## 从"比大小"到"算地址"

先回到那个让人不甘心的地方。树结构为什么是 $O(\ln n)$？因为每比较一次，只能排除一半。而"排除一半"这件事本身，就说明我们**不知道**目标在哪儿——只能一步步逼近。

数组不一样。如果键就是 $0\sim\text{TableSize}-1$ 的整数，那么

```cpp
value = array[key];        // get
array[key] = value;        // put
```

一次下标运算，$O(1)$。这里没有任何"查找"发生——地址是**算出来**的，不是找出来的。这就是 Map ADT（$(\text{key},\text{value})$ 对的集合，键唯一、值可重复）在"键是整数且范围很小"时的实现。

麻烦在于现实里的键很少这么听话，有三个障碍：

- **键不一定是整数**。姓名是字符串，坐标是浮点数，记录是结构体。
- **范围太大**。学号在 `20230001` 到 `99999999` 之间，全开成数组就是一亿格，每格 4 字节要 400 MB，而实际在册的只有几万人。
- **太稀疏**。万一键恰好只有 `1` 和 `10^9` 两个，中间九亿多个格子全是浪费。

所以"拿键当下标"这条路走不通。但三个障碍否定的都只是**键不能直接当索引**，没有一个否定"用键换出一个索引"。这中间差着一步——

> [!important] 哈希表 Hash Table
> 开一张长度为 $\text{TableSize}$ 的表（就是一个数组），再定义一个函数 $\text{hash}(\text{key})$，把键对象映射到 $0\sim\text{TableSize}-1$ 之间的整数下标。
> `get` 就是算一遍 hash 跳过去；`put` 同理。**只要 hash 是常数时间，get 与 put 就是 $O(1)$。**

关键的一步就在这里：我们并不要求键本身就是下标，只要求能**算出一个下标**。"Alice"、一串 URL、一条人员记录，全都可以通过一个函数挤进 $0\sim\text{TableSize}-1$ 这一小段整数里。

![[C9-散列表-名字到下标.png]]

上图就是全部机制：键 Alice 连同它的值（电话号码）一起被 hash 折成整数 1，于是它落在 1 号格。查的时候再算一次，还是 1。

顺带拆一下名字。**hash** 本义是"切碎、剁成小块再搅在一起"——把一个形状不定的键剁碎、揉成一个整数；中文叫**散列**（强调目的：把键散开，别挤在一处），音译就是**哈希**。名字里其实已经包含了这个结构的两条设计标准：要碎（丢信息才换得来小范围），要散（不均匀就退化）。后面所有内容都是围绕这两条展开的。

## 冲突：格子只有 TableSize 个，键有无穷多个

上一节的 $O(1)$ 有个前提没检查：算出来的格子是空的。

而这一步几乎必然不成立。键有无穷多个（所有可能的字符串、所有可能的坐标），格子只有 $\text{TableSize}$ 个。按鸽笼原理，**一定有至少两个键落到同一个下标**。这种情况叫冲突 collision，"新元素算出来的格子已经被占了"。

> [!question] 停一下
> 那我换一个好一点的哈希函数，是不是就不会冲突了？
> 不会。算一下就知道：$\text{TableSize}=10007$ 个格子，放 100 个键，至少有一对撞上的概率是
> $$1-\prod_{i=0}^{99}\frac{10007-i}{10007}\approx 39.1\%.$$
> 才 100 个键、一万个格子，就有近四成机会撞上。这就是**生日问题**：冲突的多少取决于"对数"，不取决于"格子是否够用"。所以好函数只是把撞车次数降到最少，**不能消除**。

于是设计上必须把两件事拆开做，混在一起想就会乱：

1. **函数**要把键摊匀——尽量少撞；
2. **撞了之后**要有地方收容——不能丢。

![[C9-冲突-Anna撞上Alice.png]]

上图就是冲突现场：Anna 的键也算到了 1 号格，可 1 号格里躺着 Alice。要么把 Anna 挪到别处，要么让这一格能装两个。这正好对应本讲后半部分的**两条路线**。

## 什么样的函数算"好"

评价一个哈希函数，标准只有两三条，但每一条都不像看上去那么显然：

- **摊匀**：理想情况是均匀分布——每个格子被选中的机会一样。这一条决定了冲突有多少。
- **可达**：每个格子都能被访问到。此刻它看起来像是废话（下标总是 $0\sim\text{TableSize}-1$），但等到平方探测那几节，你会发现"某些格子永远到达不了"是这门课里最实在的坑。
- **快**：hash 的代价要算进 `get` 里。如果一个"更好"的函数要 $O(n)$ 才能算出来，整个结构就白设计了。

还有一点容易被忽略：函数依赖**两件事**——键的类型，和 $\text{TableSize}$。所以"哈希函数"不是键自己的属性，**它和表长是一起选的**。换表长，同一个函数的散布就变了（这也正是后面"再散列不能直接拷贝"的根源）。

下面按"键长什么样"分三类看过去：整数、字符串、结构体。

### 整数：取模

如果键是整数，最简单也最常用的做法是取模：

$$\text{hash}(x)=x \bmod \text{TableSize}$$

```cpp
int hash( int key, int tableSize ) {
    return key % tableSize;
}
```

$\text{TableSize}=5$ 时，$\text{hash}(0)=0$、$\text{hash}(1)=1$、$\text{hash}(5)=0$、$\text{hash}(6)=1$。

这能成立，靠的是一个假设：**键本身的分布比较均匀**。如果键全是 $5$ 的倍数、表长又正好是 $5$，那么所有键都落在 $0$ 号格，表退化成一条链。这个坑先记着——它就是"表长要取素数"那一节要解决的问题。

还有一个埋伏：C++ 里负数取模保留被除数的符号，$-7 \ \%\ 5 = -2$ 而不是 $3$。现在看着无害，等写到滚动哈希时它会变成一行必须的修正。

### 字符串：三个想法，一个比一个接近

字符串不能取模，得先把一串字符变成整数。三种想法是层层递进的，每一步都解决上一步的一个毛病，也都带出新的毛病——这条链比结论本身更值得记。

**想法一：把字符的 ASCII 加起来。**

```cpp
int hash( string key, int tableSize ) {
    int hashVal = 0;
    for( int i = 0; i < key.length(); i++ )
        hashVal = hashVal + key[i];
    return hashVal % tableSize;
}
```

"A" 是 65、"n" 是 110、"a" 是 97，所以 "Anna" $=65+2\cdot110+97=382$。

两个致命伤：

- **值域太窄**。每个字符在 $0\sim127$，键最多 8 个字符，那么 $\text{hash}$ 最大也就 $127\times8=1016$，**只有前 1017 个格子可能被用到**。表长取 10007 时，用得上 $1017/10007\approx10.2\%$，将近九成的格子永远空着；更要命的是所有键都被压进这十分之一的空间里，冲突率直接放大一个数量级。
- **字母异位词全撞**。ASCII 和丢掉的是**位置信息**——哪个字母在哪一位不重要。所以 `rescued`、`secured`、`seducer` 三个词的 ASCII 和都是 **747**，永远撞在一起。

求和这条路救不回来了：它的毛病不是"和不够大"，而是"和根本不看顺序"。要救，就必须把位置算进去。

**想法二：按位置加权（$27$ 进制）。**

```cpp
int hash( Integer key, int tableSize ) {
    return (key[0] + 27 * key[1] + 27 * 27 * key[2]);
}
```

$27$ 是 $26$ 个字母加一个空格。位置越靠后权重越大，于是异位词被彻底分开（求和相同的两个词，加权和几乎一定不同）。

但这一版有三个问题：

- **只认前三位**。`abczzzz` 和 `abcdddd` 会撞；长度超过 3 的键，后面全被忽略。中文姓名、长字符串、URL 都不行。
- **假定三元组等概率**。它把 $27^3=19683$ 个三元组当成均匀分布，可自然语言不是——有些字母更常见，有些三元组（比如 `xvz`）根本不出现。结果是某些格子挤爆、某些格子空着。
- **它返回的不是下标**。返回值最大到 $127\times(1+27+729)=96139$，早就超出了表格子数，要当下标用还得再取一次模。

还有个更隐蔽的：既然底数是 $27$，每位数字就该落在 $0\sim26$。这里直接拿 ASCII 当数位，数位可能大于底数，编码就不唯一了——`(65,0,0)` 和 `(11,2,0)` 都给 $65$。真要这么写，得先把字母映射到 $0\sim26$。

**想法三：边读边乘，滚动成多项式。**

```cpp
int hash( String key, int tableSize ) {
    int hashVal = 0;
    for( int i = 0; i < key.length(); i++ )
        hashVal = 37 * hashVal + key[i];
    hashVal %= tableSize;
    if( hashVal < 0 )
        hashVal += tableSize;
    return hashVal;
}
```

三行循环，把整串字符揉成一个数：每读一个字符，就把已有的值乘 $37$ 再加进来。展开来看，它等于

$$\text{hash}=k_0\cdot37^{N-1}+k_1\cdot37^{N-2}+\cdots+k_{N-2}\cdot37+k_{N-1}.$$

这就是想法二的"加权"，只是权重变成了 $37$ 的幂、长度不再受限于 3 位。四个细节都值得停一下：

> [!important] 为什么是 37，为什么边算边取模
> **为什么乘 37**：位置信息靠"乘一个大于字符集的数"编码进高位。底数只有比字符的取值范围大，不同的字符序列才不会互相抵消；取素数是为了避免它和别的因子凑出公因数。Java 的 `String.hashCode` 用的是 **31**（结构完全一样），好处是编译器能把 $31h$ 编成 $(h\ll5)-h$，一条移位一条减法。
> **为什么必须边算边取模**：$37$ 进制长得极快，$37^5\approx6.9\times10^7$、$37^6\approx2.57\times10^9$——**第 7 个字符就已经越过 32 位 `int` 的上限** $2^{31}-1\approx2.15\times10^9$。溢出之后有符号数是未定义行为，结果不可信。数学上取模可以随时插进去，因为 $(37h+c)\bmod m=\big((37(h\bmod m)+c)\big)\bmod m$。
> **为什么最后有 `if (hashVal < 0)`**：就是整数那一节埋的伏笔。万一中途出了负数，取模还是负数，加一次 $\text{TableSize}$ 把它拉回 $0\sim\text{TableSize}-1$。
> **"边算边取模"和这段代码的差别**：这段代码把 `%` 放在**循环外面**，中间结果照样会溢出。要用在长键上，得把取模挪进循环，或者把 `hashVal` 声明成 `unsigned int`（无符号溢出是有定义的，回绕之后仍然是个"散得开"的数——指定教材就是这么写的）。

拿它算一遍："Anna" 的滚动结果是 $3447202$，对 $\text{TableSize}=10007$ 取模得 $4794$。整串字符都参与了运算，异位词不再撞，值域也不再被 8 个字符卡死。

### 结构体：把每个成员的哈希加起来

真实场景里键往往是结构体。做法是：假设每个成员自己都有哈希函数，分别算出来，**乘以不同的大素数再相加**。

```cpp
struct Person {
    string firstName;
    string lastName;
    int    age;
};

int hash( Person key, int tableSize ) {
    int hashVal = hash(key.firstName, tableSize) * 127
                + hash(key.lastName,  tableSize) * 1901
                + hash(key.age,       tableSize) * 4591;
    hashVal %= tableSize;
    if( hashVal < 0 )
        hashVal += tableSize;
    return hashVal;
}
```

最后那个 `return` 在印出来的版本里是漏掉的——声明成 `int` 却不返回值，是未定义行为（见篇末勘误）。照抄的时候别把它一起抄掉。

为什么不能简单相加？因为加法是**可交换**的。`("Jack","Smith")` 与 `("Smith","Jack")` 的三份分量完全相同，和自然相同，两个不同的人会永远撞在一起。乘上 $127$、$1901$、$4591$ 之后，同一个交换会得到不同的值：成员的"位置"被编码进了各自的权重。

为什么乘数要取素数、而且要各不相同？如果系数有公因子（比如都乘 $2$），三份贡献就带着共同的因子，取模时容易被一起约掉，等于白乘。$127$、$1901$、$4591$ 都验过是素数。

### 为什么表长要取素数

取模这一族函数有个软肋：**它只对"整除关系"敏感**。

反例：$\text{TableSize}=8$。如果所有键的哈希值都是 $8$ 的倍数（比如键本身就带一个因子 $8$，或者键是连续的 $0,8,16,\dots$），那么模 $8$ 之后全是 $0$——整张表只用得上 $0$ 号格。

由此得到规则：$\text{TableSize}$ 不该是任何"常见哈希值"的因子。取素数正好做到这一点：素数只有 $1$ 和它自己两个因子，没有小因子可以去整除一批键。

实际操作里这带来一个麻烦：表长要是素数，扩容就不能简单地"乘 2"（$2p$ 一定是偶数）。所以实现上不会现算，而是**查一张预置的素数表**，取第一个不小于 $2p$ 的素数：$11\to23\to47\to97\to197$。

> [!warning] 这里的"素数"和平方探测的"素数"不是同一件事
> 这一节要素数，是为了**摊匀**（别让某类键被系统地压到少数几格）。
> 后面平方探测、双散列也要素数，那是为了**保证探测序列能走遍全表**，别提前退化成环。
> 两条理由完全不同，但都指向同一个结论。考试喜欢把两者混在一起问一句"为什么哈希表的表长要取素数"，答的时候要分开。

### 什么能当键：不可变

原则上任何对象都能当键，只要你能给它一个像样的哈希函数。

> [!warning] 硬约束：键一旦进表，就不能再改
> 键的哈希值决定了它待在哪个格子。如果键的内容在放进表之后被修改，它的哈希值就变了——再去 `get`，算出来的是**另一个格子**，而原记录还躺在旧格子里，从此再也拿不出来。
> 所以键类型必须是**不可变**的（immutable）。Java 的 `String`、`Integer` 都是不可变的；C++ 里照抄一份键，或者干脆用 `const` 约束住。

这也解释了为什么要问"链表或二叉树能不能当键"：能，但哈希值要按内容**递归地**算（遍历所有结点），而一旦这个结构在表外被改了一个结点，表里的记录就失联了。可变结构当键，基本是自找麻烦。

> [!note] （补充）`equals` 与 `hashCode` 的契约
> Java 里给自定义类当键，必须满足：`equals` 判等的两个对象，`hashCode` 必须相等（反之不必）。因为 `HashMap.get` 是**两段式**——先按 `hashCode` 定位到桶，再在桶里用 `equals` 比较。两个"相等"的对象哈希值不同，就会被放进不同的桶，永远取不到。这是笔试里出现频率最高的哈希题。

## 两条路线：挂在旁边，还是放进里面

冲突一定要收容。而"收容"只有两种物理位置，这就把后面的全部内容分成了两大类：

- 表里那个格子已经有人了，那就把新元素放到**表外**，从那一格挂出去 —— **拉链法**；
- 表里还有空位，那就把新元素塞进**表里的空格** —— **探测法**。

| | 拉链法 Separate Chaining | 探测法 Probing |
| --- | --- | --- |
| 元素放哪 | 表外新分配的链表结点 | 表里另一个空格 |
| 负载因子 $\lambda$ | 可以 $>1$ | 必须 $\le 1$ |
| 删除 | 直接摘链，干净 | 不能真删，要留标记 |
| 缓存友好度 | 差（到处跳指针） | 好（连续数组） |
| 代码量 | 多（要一套链表） | 少 |
| 额外空间 | 每个元素一个结点 | 表里的空位 |

### 拉链法：同一个下标的都挂在一条链上

**拉链法 Separate Chaining**：把所有哈希到同一下标的元素放在一条链表上。每条链表就是一个**桶 bucket**，桶由哈希值定义。

插入很简单，而且有一个专门的选择：**插在表头**（prepend）。

```cpp
// 插入：算出下标，把新结点挂到这条链的最前面
int bucket = hash(key, tableSize);
node->next = table[bucket];
table[bucket] = node;
```

![[C9-拉链法-桶与链表.png]]

上图是 Anna 插入之后的样子：1 号桶原来是 Alice，Anna 被挂在最前面，Alice 退到第二个。为什么插表头而不是追加到末尾？因为插表头是 $O(1)$，不用走一遍链表；而"后来的先被找到"对成功的查找来说无所谓——平均位置是一样的。

查找就是"算下标，然后沿链走，比较键"。比起探测法，拉链法少了一件麻烦事：**碰撞的元素互不干扰**，链有多长只影响那一条链。

### 拉链的代价：负载因子

链有多长？这直接决定了查找要多久。用一个量把"表有多满"概括起来：

$$\lambda=\frac{N}{\text{TableSize}},$$

$N$ 是表里键的个数，$\lambda$ 就叫**负载因子 load factor**。它是平均每条链的长度。

![[C9-负载因子-十个桶.png]]

上图是一张 $\text{TableSize}=10$ 的表，装进了 $0,81,1,64,4,25,36,16,49,9$ 十个键，所以 $N=10$、$\lambda=1$。桶里的次序对应"新来的排最前"：1 号桶是 $81\to1$（1 先来），4 号桶是 $64\to4$，6 号桶是 $36\to16$，9 号桶是 $49\to9$。

现在分析查找的代价。总代价 = 算哈希（假设 $O(1)$）+ 走链。走链多久，分两种情形：

- **失败查找**（表里没有这个键）：得走完那条链的每一个结点，平均 $\lambda$ 个。
- **成功查找**（键在表里）：平均只走一半——目标在链的前半段的概率和后半段一样，平均是 $\lambda/2$——再加上目标自己那一个，共 $\lambda/2+1$ 个。

拿上图验证一下。按上面那个插入次序，每个键要摸几个结点（在链里排第几）：$1,1,2,1,2,1,1,2,1,2$，加起来 $14$，十个键平均 **$1.4$**。公式给的是 $\lambda/2+1=1.5$。差的那 $0.1$ 不是算错，而是公式的前提是"均匀散列"（每个键等概率落进任一格），这张表恰好不是。这个差距本身就是个提醒：**$\lambda$ 是一个期望，不是保证。**

设计规则也就自然出来了：**让 $\lambda\approx1$**。$\lambda$ 一大，链就长，$O(1)$ 就退化成 $O(\lambda)$，所以要扩容（再散列，见后文）。

拉链法有两个躲不开的毛病，也是它被探测法取代的理由：

- 每个元素都要 `new` 一个结点：分配开销、内存碎片，而且链表结点分散在堆上，缓存命中率差；
- 除了哈希表本身，还要写一套链表——代码量差不多翻倍。

### 探测法：把冲突的元素放进表里的空位

**探测法 Probing**（开放定址 open addressing 的一种）：不用链表，冲突时就在表里另找一个空格放进去。

![[C9-线性探测-绕回表头.png]]

上图是 11 格表的最后一次插入：$40$、$18$、$29$、$9$ 已经在 $7,8,9,10$ 四格里，新来的 $21$ 先算到 $10$，被 $9$ 占着，往下试到 $11$——越过表尾，**绕回表头**，落到 $0$ 号格。绕回（wraparound）是探测法里最容易漏掉的下标细节，写代码时就是一句 `(pos + 1) % TableSize`。

完整的插入轨迹（$\text{TableSize}=11$，$\text{hash}(x)=x\bmod 11$）：

| 依次插入 | 哈希值 | 探测路径 | 探测次数 |
| --- | --- | --- | --- |
| 40 | 7 | 7 | 1 |
| 18 | 7 | 7 → 8 | 2 |
| 29 | 7 | 7 → 8 → 9 | 3 |
| 9 | 9 | 9 → 10 | 2 |
| 21 | 10 | 10 → 0 | 2 |

**查找**用同一套逻辑：从哈希值出发，按同一个顺序试；碰到键就命中，碰到空格就停下、报告"不在表里"。

> [!important] 为什么碰到空格就可以停
> 这是探测法能成立的**全部理由**，值得停一下。
> 设键 $x$ 在表里。插入它的那天，它的探测路径上第一个空格被它占了。那么今天沿同一条路径走过来，在碰到它之前**不可能遇到空格**——一旦遇到空格，说明它当初根本没走到这里，也就是说它不在表里。
> 换句话说，空格是"这条路径到此为止"的证书。**这条不变量是探测法的地基**，下一节讲删除时会看到它有多脆。

表满的判据：$\lambda=N/\text{TableSize}\le1$；$\lambda=1$ 就是满。这也意味着探测法**用不上全部空间**——它总要留一点余量，否则一次失败的查找要走到表尾才敢停。

### 三种探测策略，写成同一个公式

所有探测策略都能用一个式子描述：第 $i$ 次探测的位置是

$$\big(\text{hash}(x)+f(i)\big)\bmod \text{TableSize}.$$

区别只在 $f(i)$：

| 策略 | $f(i)$ | 从 $\text{hash}(x)=7$、表长 11 出发的探测位置 |
| --- | --- | --- |
| 线性探测 Linear Probing | $i$ | 7 → 8 → 9 → 10 → 0 → … |
| 平方探测 Quadratic Probing | $i^2$ | 7 → 8 → 0 → 5 → 1 → 10 → … |
| 双散列 Double Hashing | $i\cdot\text{hash}_2(x)$ | 7 → $7+s$ → $7+2s$ → …（$s$ 由第二个函数定） |

$i$ 从 $0$ 开始算，所以 $i=0$ 那一次就是"先试自己的哈希值"。

### 线性探测：一次聚集

线性探测有两个好处：只要表里还有空格就一定能找到（顺着走总能走遍全表）；格子是连续访问的，缓存最友好——它是三种策略里唯一"内存友好"的。

但它有一个结构性毛病，叫**一次聚集 primary clustering**。

![[C9-一次聚集-整块不可用.png]]

上图的 $40$、$51$、$18$ 都算到 $7$，依次落进 $7$、$8$、$9$，三格连成一块。这一块的后果是：**算到 7 的键，从此都要从 8 开始试**。块越长，新来的键落到块后面的概率越大，块就越长——一个正反馈。

（这里要说清楚一件事：受影响的只是"算到 7"的键。算到 6 的键如果 6 号格空着，它就直接落在 6，跟这一块毫无关系。把块想成"对所有更小的下标都不可用"是错的——见篇末勘误。）

正反馈有多凶？继续往表里加，让 $\lambda$ 逼近 1：

![[C9-一次聚集-绕半圈找空位.png]]

先插入 $39$（算到 $6$，落在 $6$），$17$ 算到 $6$，于是走 $6\to7\to8\to9\to10$，**5 步**才落到 $10$。接着插入 $6$，同样算到 $6$，可这时 $6\sim10$ 全被占，绕回表头 $0\sim4$ 也全被占，直到 $5$ 号格才空——**11 步，走遍整张表**。

注意此刻 $\lambda=10/11\approx0.91$，只是"快满了"，最后那一步花了 11 次探测。一次聚集的可怕之处不在"多撞几次"，而在**它让探测次数的增长远快于 $\lambda$ 的增长**。

> [!note] （补充）教科书给的期望值
> 线性探测（均匀散列假设下）：成功查找约 $\frac12\big(1+\frac{1}{1-\lambda}\big)$，失败查找约 $\frac12\big(1+\frac{1}{(1-\lambda)^2}\big)$。$\lambda$ 只要到 $0.9$，失败查找的期望就是 $50.5$ 次——比成功的 $5.5$ 次差了将近十倍。这就是为什么线性探测的表要压在 $\lambda\approx0.5$ 附近。

### 平方探测：跳着走

既然"撞了就试下一格"会造成长块，那就别试下一格，**跳着走**：

$$f(i)=i^2 .$$

第一次撞了跳 $1$，第二次跳 $4$，第三次跳 $9$……两个撞在一起的键，下一次探测就被甩开，不再形成连续的块，**一次聚集消失**。

代价是：**表长必须是素数**。

![[C9-平方探测-非素数表卡死.png]]

上图：$\text{TableSize}=8$（不是素数），$\text{hash}(19)=19\bmod8=3$。从 $3$ 出发的平方探测序列是

$$3+f(i)\bmod 8 = 4,\ 7,\ 4,\ 3,\ 4,\ 7,\ 4,\ 3,\dots$$

——只在 $3,4,7$ 三格里打转。表里 $1,2,5,6$ 四格明明空着，**就是到不了**。

原因在 $i^2$ 的取值上：$i$ 从 $0$ 到 $7$，$i^2 \bmod 8$ 只可能是 $\{0,1,4\}$，加上起点 $3$ 就只剩三个落点。表长是素数时，$i^2$ 能取到的剩余类多得多，探测序列才铺得开。

（这张图里 $9$ 被画在 $0$ 号格，可 $\text{hash}(9)=1$、而 $1$ 号格空着——从 $1$ 出发的平方探测也到不了 $0$。格子里放哪个数不影响"非素数会困住"这个结论，见篇末勘误。）

**但素数还不够。** 第二层问题更隐蔽：

![[C9-平方探测-过半装载不可达.png]]

$\text{TableSize}=11$ 是素数，$\text{hash}(11)=0$。从 $0$ 出发的探测序列是

$$0+f(i)\bmod 11 = 1,\ 4,\ 9,\ 5,\ 3,\ 3,\ 5,\ 9,\dots$$

能到的格子只有 $\{0,1,3,4,5,9\}$ 六个。$2,6,8$ 三个格子空着，却永远到不了。此时 $\lambda=7/11\approx0.64$——刚过一半，就已经插不进去了。

所以平方探测多了一条硬规则：**装载不能超过一半**。为什么"一半"是那个分水岭，下一节给证明。

> [!note] （补充）二次聚集
> 平方探测消掉了一次聚集，但没有完全消掉"扎堆"：两个键如果**起点相同**（哈希值一样），它们的探测序列完全一样，从此一路同行。这叫**二次聚集 secondary clustering**。它比一次聚集轻得多（不是连续的块，不会越滚越大），但确实存在——真正消掉它的办法是双散列。

### 半张表够用：平方探测定理

> [!important] 定理
> 设表长 $p$ 是素数。平方探测的前 $\lfloor p/2\rfloor+1$ 个位置互不相同。因此只要装载不超过一半（$N\le p/2$），一定能找到空格。

**证明（反证）**。设有两个不同的探测次数 $i<j$ 落在同一格：

$$\big(h+i^2\big)\equiv\big(h+j^2\big)\pmod p\;\Longrightarrow\;(j-i)(j+i)\equiv0\pmod p .$$

$p$ 是素数，所以 $p$ 必须整除两个因子之一：

- **$p\mid(j-i)$**：可 $0<j-i<p$，区间里没有 $p$ 的倍数，不成立。
- **$p\mid(j+i)$**：可 $0<j+i\le2\cdot\lfloor p/2\rfloor=p-1<p$（$p$ 是奇素数），区间里同样没有 $p$ 的倍数。

两条都不可能，所以这样的 $i,j$ 根本不存在，前 $\lfloor p/2\rfloor+1$ 个位置两两不同。$\blacksquare$

**为什么这就保证了能找到空格**：装载不超过一半时被占用的格子不超过 $\lfloor p/2\rfloor$ 个，而探测序列给出 $\lfloor p/2\rfloor+1$ 个互不相同的位置——**位置比被占的格子还多一个**。既然这些位置彼此不同，它们不可能全挤在那些被占的格子里，所以至少有一个位置是空的。

$p=11$ 时手算一遍：$i=0\dots5$ 给出 $0,1,4,9,5,3$ 六个位置，两两不同；到 $i=6$ 才开始重复（$36\bmod11=3$）。

原稿把定理写成"前 $\text{TableSize}/2$ 个位置互不相同"，可它自己的证明用的是 $0\le i<j\le\text{TableSize}/2$，也就是 $\text{TableSize}/2+1$ 个位置。差的这一个，正好是"半数装载还能不能找到"的那一个——见篇末勘误。

### 双散列：步长自己算

平方探测的步长是固定的 $1,4,9,\dots$，跟是哪个键无关。那就再进一步：**让步长由键自己决定**。

$$f(i)=i\cdot\text{hash}_2(x).$$

$\text{hash}_2$ 是第二个哈希函数，它算出来的不是位置，而是**步长**——这个键每次往后跳多远。

![[C9-双散列-按步长跳跃.png]]

例子：$\text{TableSize}=11$，$\text{hash}(x)=x\bmod11$，$\text{hash}_2(x)=5-(x\bmod5)$。

| 键 | $\text{hash}$（起点） | $\text{hash}_2$（步长） | 探测路径 | 次数 |
| --- | --- | --- | --- | --- |
| 40 | 7 | $5-0=5$ | 7 | 1 |
| 84 | 7 | $5-4=1$ | 7 → 8 | 2 |
| 62 | 7 | $5-2=3$ | 7 → 10 | 2 |
| 29 | 7 | $5-4=1$ | 7 → 8 → 9 | 3 |

**同样从 7 出发，后三个键走出了三条不同的路**：$62$ 一步跳到 $10$，$29$ 顺着 $84$ 走过的步长 $1$ 挪到 $9$。既没有一次聚集，也几乎没有二次聚集——这正是双散列比平方探测更均匀的原因。

但 $\text{hash}_2$ 选不好会出人命：

![[C9-双散列-步长为零.png]]

如果偷懒写成 $\text{hash}_2(x)=x\bmod\text{TableSize}$，那么 $\text{hash}_2(11)=11\bmod11=0$，于是 $f(i)=i\cdot0=0$——**探测序列永远是同一个位置**。上图里 $0$ 号格被 $22$ 占了，新来的 $11$ 算出来也是 $0$，试一万次还是 $0$。表里还有 $6$ 个空格，$11$ 就是插不进去。

正确的选法是

$$\text{hash}_2(x)=R-(x\bmod R),\qquad R\ \text{是小于表长的素数},$$

这样步长落在 $1\sim R$，**永远不为 $0$**。

为什么表长还必须是素数？这次的理由比平方探测那条更好懂：步长 $s$ 与表长 $p$ **互素**时，序列 $h,\,h+s,\,h+2s,\dots$ 才能走遍全表（$s$ 在模 $p$ 下可逆，$i\cdot s$ 能取遍所有剩余类）。$p$ 是素数、$s<p$，互素自动成立。要是表长是合数而步长恰好是它的因子，序列就会退化成一个小圈——和平方探测那张 $8$ 格表的毛病是同一个。

## 删不掉的一格：探测表的删除（补充）

这一节在材料之外，按指定教材补。它是探测法必然的缺口，而且是最常考的一道"为什么"。

拉链法删除很干净：找到结点，从链上摘掉。探测法**不行**——**不能直接把格子清空**。

具体一点。11 格表，依次插入 $40$、$18$、$29$，它们落在 $7$、$8$、$9$。现在删除 $18$，把 $8$ 号格清空。

再查 $29$：算到 $7$，$7$ 号格是 $40$ 不是它，继续到 $8$——**空的**——按规则"遇到空格就停"，报告 $29$ 不在表里。可 $29$ 明明就在 $9$ 号格。

错在哪儿？清空打破了上一节那条不变量（"插入时路径上的第一个空格被它占了"）。空格一旦出现在路径中间，后面的元素就被凭空"切断"了。

三种解法，按代价排：

1. **懒惰删除 lazy deletion**：格子不置空，改置一个专用的"已删除"标记。查找时把标记当作"已占用"继续往后走；插入时则可以复用它。代价是标记攒多了，表看着满其实没几个元素，探测会变慢——所以要维护一个"已用格数"计数器，到了阈值就再散列。
2. **把后面的元素重新插入**：删一个要搬一串，代价 $O(n)$，一般不这么做。
3. **改用拉链法**：没有这个问题。

> [!warning] 一句话答案
> 为什么开放定址的哈希表不能直接删除元素？因为"空格"同时承担了两个含义——**没有这个键**和**这个格子空着**。删除会在探测路径中间制造一个假空格，让后面的元素全部失联。

## 装不下了：再散列

三种策略各有各的"装不下"，而且症状不一样：

| 策略 | 症状 | 该动手的时机 |
| --- | --- | --- |
| 拉链法 | 链太长，$O(1)$ 退化成 $O(\lambda)$ | $\lambda\approx1$ |
| 线性探测 | 一次聚集、探测次数陡增 | $\lambda\approx0.5\sim0.7$ |
| 平方探测 / 双散列 | **直接插不进去**（过半就有格子不可达） | $\lambda=0.5$ |

三种都指向同一个动作：**换一张更大的表**，把现有的元素搬过去。这个操作叫**再散列 rehashing**。

> [!warning] 不能直接拷贝数组
> 因为哈希值依赖 $\text{TableSize}$：
> - 取模的除数变了（$11\to23$），同一个键的落点就变了；
> - 探测的绕回点也变了，碰撞关系全变；
> - 所以"把旧数组整段拼过来"是错的。必须**把 $N$ 个元素逐个重新插入新表**。

代价：搬 $N$ 个，每次 $O(1)$，共 $O(N)$。新表多大？乘 2——但前面说过 $2p$ 一定是偶数，跟"表长取素数"直接冲突。所以实际取的是**第一个不小于 $2p$ 的素数**：$11\to23\to47\to97\to197$。

这个 $O(N)$ 会不会让插入变成 $O(N)$？不会，因为搬运不是每次插入都发生，而且表每次翻倍，越往后搬得越稀。

从 $11$ 格开始一路插到 $100$ 个键，数一下：第 $6$、$12$、$24$、$49$、$99$ 个键进来时触发扩容（每次都是 $\lambda$ 刚过 $0.5$），分别搬 $6,12,24,49,99$ 个元素，**合计 190 次搬移**。也就是每插入一次平均多搬 $1.9$ 个——常数。这跟栈的倍增扩容是同一个均摊论证（见 [[C3.1 栈 Stack]]）。

> [!note] （补充）真实实现里的两个变体
> 1. **不要求素数也能活**：Java 的 `HashMap` 把容量固定成 $2$ 的幂，用 `(n-1) & hash` 代替取模（对 $2$ 的幂来说两者等价），再拿一个"扰动函数" $h\oplus(h\gg16)$ 把高位混进低位来补偿。省掉除法，代价是表长不再是素数。这说明"素数表长"是**充分**选择，不是必要条件。
> 2. **阈值取不同**：Java 默认负载因子 $0.75$；Python 的 `dict` 用开放定址，装载到约 $2/3$ 就扩容。

## 哈希表换到了什么，丢掉了什么

把镜头拉远。哈希表拿到的是一句"期望 $O(1)$"，代价是两样东西。

**一、顺序。** 表里根本没有"谁在谁前面"这回事——位置只由哈希值决定，跟大小无关。于是二叉搜索树那些拿手好戏全没了：

- `findMin` / `findMax`：退化成扫全表 $O(N)$；
- 按序遍历：不存在这回事；
- 范围查询（"年龄在 18 到 30 之间的人"）：要么扫全表，要么先排序。

这就是为什么标准库同时给你两套容器，而不是用哈希表取代树。

**二、最坏情况。** $O(1)$ 是**期望**，不是保证。所有键撞进同一个桶时，它退化成一条链，$O(N)$；而且更麻烦的是，这个最坏情况可以被**人为制造**：哈希函数是公开且确定的，攻击者可以预先算出一批互相冲突的键，把 $N$ 次操作从 $O(N)$ 拖进 $O(N^2)$——这类攻击叫 hash flooding / hash DoS，PHP、Java、Python 都中过招。现代对策是给哈希加一个**进程级随机种子**（Python 的 `PYTHONHASHSEED`、`SipHash` 这类带密钥的函数），让攻击者算不出冲突。

| | BST / AVL / 红黑树 | 哈希表 |
| --- | --- | --- |
| 期望代价 | $O(\ln N)$ | $O(1)$ |
| 最坏代价 | $O(\ln N)$ | $O(N)$ |
| 有序遍历 | 有 | 无 |
| 范围查询 | $O(\ln N+k)$ | $O(N)$ |
| `findMin` / `findMax` | $O(\ln N)$ | $O(N)$ |
| 每个元素的额外空间 | 两个指针 | 表内空位（探测）/ 结点（拉链） |

选哪个，取决于你要不要顺序，而不是哪个更"高级"。**哈希表是用"顺序"换"常数时间"的结构**——这句话值得背下来，它同时解释了两件事：为什么树不会被淘汰，以及为什么面试官爱问"什么场景该用哈希表"。

> [!note] （补充）各语言里的对应物
> - **C++**：`std::unordered_map` / `std::unordered_set`（哈希），`std::map` / `std::set`（红黑树）。自定义键要特化 `std::hash<K>`。
> - **Java**：`HashMap` / `HashSet`（哈希，链地址法 + 链表过长时转红黑树），`TreeMap` / `TreeSet`（红黑树）。键必须正确实现 `equals` 与 `hashCode`。
> - **Python**：`dict` / `set` 都是开放定址 + 扰动，没有树版本（`OrderedDict` 只是额外记住插入顺序）。

## 速查

| 量 | 公式 / 做法 | 备注 |
| --- | --- | --- |
| 哈希表 | 数组 + $\text{hash}(\text{key})\to0\sim\text{TableSize}-1$ | `get`/`put` 期望 $O(1)$ |
| 整数 | $x\bmod\text{TableSize}$ | 要求键本身分布较匀 |
| 字符串 | $h=37h+c$，**边算边取模** | Java 用 $31$；$37^6>2^{31}$ |
| 结构体 | 各成员哈希乘不同素数再相加 | 不能直接相加（可交换） |
| 冲突 | 必然发生（鸽笼 + 生日问题） | $10007$ 格放 $100$ 键，撞上概率约 $39\%$ |
| 负载因子 | $\lambda=N/\text{TableSize}$ | 拉链的平均链长 |
| 拉链：成功 / 失败 | $\lambda/2+1$ / $\lambda$ | 设计目标 $\lambda\approx1$ |
| 线性探测 | $f(i)=i$ | 一次聚集；缓存友好 |
| 平方探测 | $f(i)=i^2$ | 表长素数，且 $\lambda\le0.5$ |
| 双散列 | $f(i)=i\cdot\text{hash}_2(x)$，$\text{hash}_2=R-(x\bmod R)$ | 步长 $\ne0$ 且与表长互素 |
| 探测表满 | $\lambda\le1$，$\lambda=1$ 即满 | 删除须留标记（惰性删除） |
| 表长 | 取素数 | 摊匀 + 保证探测可达 |
| 再散列 | 取 $\ge2\text{TableSize}$ 的第一个素数，逐个重插 | 均摊 $O(1)$；$11\to23\to47\to97\to197$ |

探测代价的期望值（均匀散列假设，单位：次探测）：

| $\lambda$ | 线性：成功 | 线性：失败 | 平方 / 双散列：成功 | 平方 / 双散列：失败 |
| --- | --- | --- | --- | --- |
| 0.25 | 1.167 | 1.389 | 1.151 | 1.333 |
| 0.50 | 1.500 | 2.500 | 1.386 | 2.000 |
| 0.75 | 2.500 | 8.500 | 1.848 | 4.000 |
| 0.90 | 5.500 | 50.500 | 2.558 | 10.000 |

（线性探测：成功 $\frac12\big(1+\frac{1}{1-\lambda}\big)$，失败 $\frac12\big(1+\frac{1}{(1-\lambda)^2}\big)$；平方探测与双散列：成功约 $-\frac{\ln(1-\lambda)}{\lambda}$，失败约 $\frac{1}{1-\lambda}$。）
