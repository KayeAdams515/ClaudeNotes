## 一、课件的对比表（原样）

| 指标 Indicators | | **Sequential Storage 顺序存储** | **Linked Storage 链式存储** |
| --- | --- | --- | --- |
| **Space 空间** | Room/Capacity 容量 | **Pre-allocated**, maybe redundant maybe insufficient（预分配，可能冗余也可能不够） | **Dynamic allocated, just perfect**（动态分配，不多不少） |
| | Storage Density 存储密度 | **High, only data**（高，只存数据） | **Low, because of the pointers**（低，因为要存指针） |
| **Time 时间** | Access/retrieve 存取 | **Random access $O(1)$**（随机存取） | **Sequential access $O(n)$**（顺序存取） |
| | Insert and erase 增删 | **$O(n)$** | **If located, $O(1)$**（若已定位则 $O(1)$） |
| **When to use 何时使用** | | ① capacity is **known** 容量已知<br>② **seldom** insert or delete 很少增删 | ① capacity is **unknown** 容量未知<br>② **frequently** insert or erase 频繁增删 |

## 二、逐行读懂这张表

### 2.1 容量：预分配 vs 动态分配

> [!note] "maybe redundant maybe insufficient" 的双输局面
> 顺序表必须在构造时说出 capacity：
> - 估大了 → 大量格子空着，**空间浪费**（[[C2.2 案例：字母表·花名册·多项式]] 里稀疏多项式开 20001 格只用 3 格就是极端例子）；
> - 估小了 → 装满后无法插入（课件的 `insert` 直接 `return false`），或者触发扩容，付出 $\Theta(n)$ 的拷贝代价（[[C1.6 代码复杂度的计算方法]] 的 `update_capacity`）。
>
> **"预先决定大小"这件事本身就是错误的来源**——链表把这个决定推迟到了每次插入的那一刻。

### 2.2 存储密度：高 vs 低

$$\text{存储密度} = \frac{\text{数据本身占用的空间}}{\text{结点实际占用的总空间}}$$

| 结构 | 存 `int`（4B），64 位指针（8B） | 密度 |
| --- | --- | --- |
| 顺序表 | 4B / 4B | **100%** |
| 单链表 | 4B / (4+8)B = 12B | **≈33%** |
| 双链表 | 4B / (4+8+8)B = 20B | **≈20%** |

> [!warning] 但这只是账面数字
> 顺序表如果预留了一半空间没用，**实际利用率也只有 50%**。所以"存储密度高"要配合"容量估得准"才真正成立。
> 真正的比较应该是：**顺序表浪费在"预留的空格"上，链表浪费在"每个结点的指针"上**。哪个更亏，取决于你对容量的估计有多准。

### 2.3 存取：随机 vs 顺序

> [!important] 这一行是两者最本质、最不可调和的差异
> 顺序表能算地址（$Loc(e_i)=L_0+(i-1)m$），所以 $O(1)$；链表只能顺着指针走，所以 $O(n)$。
> **这条差异无法通过任何技巧弥补**——除非放弃"结点位置任意"这个前提，而那样它就不是链表了。

### 2.4 增删：$O(n)$ vs "若已定位则 $O(1)$"

> [!warning] "If located" 这四个字是全表最重要的限定语
> - 顺序表增删的 $O(n)$ 花在**搬移元素**上（平均 $n/2$ 或 $(n-1)/2$ 次，见 [[C2.4 顺序表实现]]）；
> - 链表增删的 $O(1)$ 只算**改指针**，前面**找位置**的 $O(n)$ 没算进去。
>
> 所以"从第 $i$ 个位置插入"这个完整操作，**两者都是 $O(n)$**，只是慢在不同的地方。链表真正胜出的场景是：
> 1. **头插头删**（链表 $O(1)$，顺序表 $O(n)$）；
> 2. **已经持有结点指针**（如 LRU 中哈希表直接给出指针）；
> 3. **遍历过程中边走边删**（游标已经在那里了）。

> [!note] 现实中的反直觉：小数据量下链表常常输
> 理论上链表增删更快，但实测中 $n$ 不大时 `std::vector` 往往比 `std::list` 快，原因有二：
> 1. **缓存局部性**：数组连续存放，一次缓存行加载能拿到多个元素；链表结点散落各处，几乎每次跳转都是一次缓存未命中（cache miss），代价可达上百个时钟周期。
> 2. **`new`/`delete` 的真实开销**：链表每插入一个元素就要向分配器要一次内存，比数组的 memmove 拷贝贵得多（[[C1.6 代码复杂度的计算方法]] 里 `new delete` 被特意标红就是这个意思）。
>
> **理论复杂度选算法，缓存行为定胜负** —— 这是 $\Theta$ 记号故意丢掉的那个常数在现实中的反扑。

## 三、选型准则

> [!important] 课件的 When to use
> **用顺序存储**：① 容量已知；② 很少插入删除。
> **用链式存储**：① 容量未知；② 频繁插入删除。

> [!note] 再加两条实用判据
> 3. **是否需要随机访问**：要频繁按下标取第 $k$ 个 → 顺序表（链表这里是 $O(n)$，几乎判死刑）。
> 4. **元素本身有多大**：元素很大时链表的指针开销占比变小，且顺序表搬移一个大元素代价高 → 倾向链表（或顺序表存指针）。
>
> 一句话记忆：**查得多用顺序表，改得多用链表；大小已知用顺序表，大小不定用链表。**

## 四、两种实现的完整对照

| 维度           | 顺序表 SqList    | 单链表 LL                            |
| ------------ | ------------- | --------------------------------- |
| 逻辑关系靠什么表达    | **位置相邻**      | **指针**                            |
| 是否需要预知大小     | 需要            | 不需要                               |
| 存储密度         | 1（最高）         | < 1                               |
| 按下标取值 get    | $O(1)$        | $O(n)$                            |
| 按值查找 find    | $O(n)$        | $O(n)$                            |
| 头部插入/删除      | $O(n)$        | $O(1)$                            |
| 尾部插入         | $O(1)$（未满时）   | $O(1)$（有 tail）/ $O(n)$（无 tail）    |
| 中间插入/删除（含定位） | $O(n)$        | $O(n)$                            |
| 中间插入/删除（已定位） | $O(n)$（仍要搬）   | $O(1)$（单链需前驱，双链直接可删）              |
| 空间是否会浪费      | 会（预留的空格）      | 会（每结点的指针）                         |
| 缓存友好性        | **好**         | 差                                 |
| 对应的 STL 容器   | `std::vector` | `std::forward_list` / `std::list` |

## 本节自测 Self-Test

> [!question] Q1：顺序表和链表在"空间"上各自浪费在哪里？
> **A**：顺序表浪费在预分配却未使用的空格；链表浪费在每个结点的指针域。

> [!question] Q2：表中"Insert and erase: If located, $O(1)$"这句话的完整含义是什么？
> **A**：只有已经持有目标位置的指针时改指针才是 $O(1)$；从头定位仍需 $O(n)$，因此完整的"按序号插入"两者都是 $O(n)$。

> [!question] Q3：存 int 的单链表存储密度是多少（64 位系统）？
> **A**：4/(4+8) ≈ 33%。

> [!question] Q4：什么情况下应该选顺序存储？什么情况下选链式？
> **A**：容量已知且很少增删 → 顺序；容量未知或频繁增删 → 链式。再补两条：需频繁随机访问 → 顺序；元素很大 → 倾向链式。

> [!question] Q5：为什么实测中小规模数据 `vector` 常常比 `list` 快？
> **A**：数组连续存放，缓存命中率高；链表每次插入都要 new，且指针跳转造成大量缓存未命中。理论复杂度忽略的常数在此起决定作用。

> [!question] Q6：LeetCode 第 2 题和本章哪个内容同构？
> **A**：与 2.2 节的多项式链式相加同构——两条有序链同步归并，处理进位/合并与剩余部分。
